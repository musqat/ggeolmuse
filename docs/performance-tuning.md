전·후 수치는 잰 조건과 같이 둔다. 조건이 빠지면 나중에 비교가 안 된다.

[시행착오](trial-and-error.md) 에 따로 있다. 여기는 줄인 것만 모았다.

## 시작하며

느리다는 말은 세 군데서 나왔다. 백테스트가 5년치를 돌리면 100초가 걸렸고,
CI 가 4분에서 11분이 됐고, 노드가 비어 있는데 파드가 못 들어갔다. 셋 다 처음
짚은 데가 원인이 아니었다.

잰 도구는 항목마다 다르다.

```
curl -w                  응답 크기 · 시간
k6                       서비스별 요청률
kubectl top / describe   실사용 · 요청 합계
CI 로그 타임스탬프        단계별 소요
```

수치를 적는 규칙은 둘이다. **같은 조건에서 잰 값만 나란히 둔다.** 캐시 히트와
미스의 차이를 "90% 개선" 으로 적으면 최적화로 읽힌다. **계산값은 계산값이라고
적는다.** 배포 전에는 건수 × 건당으로 적어 두고 배포 뒤 같은 명령으로 다시 쟀다.

<br>

## 개선 방향

줄일 데를 찾는 순서가 있다.

```
1  요청 수      부르지 않으면 제일 싸다
2  응답 크기    부르되 덜 받는다
3  캐시         받은 걸 다시 쓴다. 대가가 있다
4  자원 요청    요청값과 실사용을 맞춘다
5  CI           기다리는 시간을 없앤다
```

앞쪽이 싸고 확실하다. 2,000회를 2회로 만든 것이 캐시 계층을 얹은 것보다 컸다.

<br>

## 개선 1. 요청 수를 줄였다

### 1.1 백테스트가 날짜마다 API 를 불렀다

**문제.** 5년치 백테스트가 100초 걸리고 500 이 났다.

**원인.** DB 는 정상이었다. slow query 로그가 50ms 안쪽이었고 데이터도 다 있었다.
market-data 로그를 보고서야 알았다. 전략 실행 루프가 하루씩 돌며 가격과 환율을
개별로 받는다. 5년이면 약 2,000회다.

**개선.** 범위를 한 번에 받는 API 로 바꿨다.

**결과.**

| | 전 | 후 |
|---|---|---|
| market-data 호출 | 약 2,000회 | 2회 |
| 응답 | 100초 | 1.5초 |

| | |
|---|---|
| 조건 | 5년치 백테스트 한 건 |
| 확인 | 같은 기간을 다시 돌려 1.5초. market-data 로그에 호출 2건 |

경위는 [백테스트 5년치가 100초 걸렸다](problem-solving.md#백테스트-5년치가-100초-걸렸다).

### 1.2 환율을 종목마다 불렀다

**문제.** 부하 중 서비스별 요청률을 보니 market-data 만 자릿수가 달랐다.

```
게이트웨이      208 rps    사용자 요청
backtest        207 rps    그대로 전달
market-data   2,216 rps    10.7배
```

**원인.** 종목 분석 1건당 market-data 를 6.4회 부른다. 그중 `fx/latest` 는 값이
하나인데 종목마다 불렀다.

**개선.** wrapper 에 60초 캐시를 뒀다.

**결과.** 백테스트 다섯 번에 한 번만 나간다.

| | |
|---|---|
| 조건 | 로컬 k6, 조회 API (`symbols` / `price` / `ohlc`) |
| 확인 | 같은 부하에서 `fx/latest` 요청률 |

경위는 [요청 하나가 10.7 배로 증폭됐다](problem-solving.md#요청-하나가-107-배로-증폭됐다).

### 1.3 헤더가 종목 목록을 따로 받았다

**문제.** 새로고침마다 같은 종목 목록을 두 벌 받았다.

**원인.** 부르는 곳이 넷인데 방식이 둘로 갈렸다.

```
Charts · Backtest · Trading    useQuery(['stock', 'symbols'])   캐시 공유
Header                         useEffect + useState              자기 사본
```

Header 만 React Query 밖이라 셋이 나눠 쓰는 캐시를 못 봤다.

**개선.** 같은 키로 옮겼다. 넷 중 누가 먼저 뜨든 한 번만 받는다.

**결과.**

| | 전 | 후 |
|---|---|---|
| 새로고침 한 번 | 2회 | 1회 |
| 페이지 이동 | 0회 | 0회 |

Header 가 `Routes` 밖에 있어서 페이지를 옮겨도 다시 받지 않는다. 줄어드는 건
새로고침 한 번 분이다. `staleTime` 10분 안에는 넷 다 캐시를 쓴다.

| | |
|---|---|
| 조건 | 코드 경로. `useEffect([])` 는 마운트에 한 번, Header 는 언마운트 안 됨 |
| 확인 | 타입 검사 · 린트 통과, E2E 35개 통과 (#131) |

## 개선 2. 응답을 줄였다

### 2.1 종목 목록이 3,227 KB 였다

**문제.** `/api/market/symbols` 가 같은 서버의 다른 응답과 자릿수가 달랐다.

```
/api/market/symbols            3,227 KB
/api/market/stocks?size=20       5.2 KB
/api/market/price/AAPL          0.23 KB
```

14,849건, 필드 10개, 건당 약 217 B.

**원인.** Asset 을 통째로 직렬화한다. 받는 쪽 넷(Header · Backtest · Charts ·
Trading)이 전부 `symbol` 하나만 읽는다. 나머지 아홉 필드는 파싱하고 버린다.

**개선.** QueryDSL 프로젝션으로 티커만 뽑고 `active = true` 로 걸렀다. 상장폐지
2,322건이 검색에 뜰 이유가 없다.

```java
queryFactory
    .select(asset.symbol)
    .from(asset)
    .where(asset.active.isTrue())
    .orderBy(asset.symbol.asc())
    .fetch();
```

**결과.**

| | 전 | 후 |
|---|---|---|
| 건수 | 14,849 | 12,527 |
| 건당 | 약 217 B | 17.8 B |
| 크기 | 3,227 KB | 223 KB |

배포 전 계산값은 188 KB 였다. 건당을 15 B 로 잡았는데 실제는 17.8 B 다.

| | |
|---|---|
| 조건 | 운영, `curl -s -o /dev/null -w '%{size_download}'`. 2026-09-06 배포 뒤 실측 |
| 확인 | 응답 12,527건, 각 항목이 `{"symbol":"A"}` 꼴. 응답 계약이 바뀌어 E2E 넷을 같이 고쳤고 35개 통과 (#126, #130). 응답이 `symbol` 하나뿐인 것과 상장폐지 제외는 통합 테스트가 고정한다 |

<br>

## 개선 3. 캐시를 다시 봤다

### 3.1 Redis 캐시는 히트와 미스의 차이다

**문제.** "Redis 로 응답 90% 개선" 이라고 적혀 있었다.

**원인.** 같은 백테스트를 캐시가 없을 때와 있을 때 돌린 값이다. 서버가 빨라진 게
아니다. 첫 요청은 그대로 1.2초고 두 번째부터 150ms 다.

**개선.** 수치는 그대로 두고 조건을 붙였다.

**결과.**

| | 응답 |
|---|---|
| 캐시 없음 | 1.2초 |
| 캐시 있음 | 150ms |

| | |
|---|---|
| 조건 | 같은 백테스트 요청 두 번. 첫 번째가 미스, 두 번째가 히트 |
| 확인 | 캐시 비우고 다시 두 번 |

### 3.2 캐시 키를 기간에서 일자로 바꿨다

**문제.** 캐시가 있는데 히트가 거의 없었다.

**원인.** 기간 단위로 키를 잡으면 요청 범위가 조금만 달라도 어긋난다.

**개선.** 일자별로 쪼갰다. 겹치는 날짜가 재사용된다.

**결과.** 히트율 77% 를 봤다. **표본이 적어 대푯값으로 보긴 어렵다.** 숫자보다
바꾼 것이 남는다.

대가가 있었다. 범위 조회가 날짜 수만큼 왕복하게 됐다. 2년치가 4.5초가 되고
게이트웨이 타임아웃에 걸려 405 로 나왔다.

```
히트율     거의 없음 → 77% (표본 적음)
왕복       1회 → 날짜 수만큼
2년치      → 4.5초, 타임아웃
```

| | |
|---|---|
| 조건 | 백테스트 요청, 캐시 히트 카운터 |
| 확인 | 히트율과 함께 범위 조회 응답 시간. 그게 4.5초로 튄 걸로 대가를 알았다 |

경위는 [기간 단위 캐시는 히트가 없었다](trial-and-error.md#기간-단위-캐시는-히트가-없었다)
와 [타임아웃인데 405 가 나왔다](problem-solving.md#타임아웃인데-405-가-나왔다).

## 개선 4. 자원 요청을 실사용에 맞췄다

`requests` 는 스케줄링에만 쓰인다. 실사용보다 크게 잡으면 노드가 비어 있어도
파드가 못 들어간다.

### 4.1 requests 가 limits 의 절반이었다

**문제.** `kafka-0` 이 `Pending` 으로 멈췄다. 400m 이 들어갈 자리가 없었다.

```
kubectl describe node
cpu  3800m (95%)   4 vCPU 노드
```

**원인.** 자바 서비스 다섯의 `requests` 를 기계적으로 `limits / 2` 로 넣어뒀다.
템플릿 문제로 렌더링이 안 되다가 고쳐지면서 1,450m 이 한꺼번에 잡혔다.

**개선.** 실사용을 재고 그 기준으로 다시 잡았다.

| 파드 | 요청 | 실사용 |
|---|---|---|
| gateway-server | 300m | 11m |
| keycloak | 250m | 3m |
| frontend-web | 250m | 0m |
| redis | 150m | 6m |
| zookeeper | 150m | 1m |

`limits` 는 그대로 뒀다. 기동할 때 쓰는 양이라 건드리면 부팅이 느려진다.
`config-server` 만 150m → 200m 으로 올렸다. 나머지가 전부 이 서버를 기다린다.

**결과.**

| | 전 | 후 |
|---|---|---|
| CPU requests 합계 | 3,800m (95%) | 1,300m |

| | |
|---|---|
| 조건 | 4 vCPU 단일 노드, `kubectl top` 실사용. 2026-09-01 |
| 확인 | `kafka-0` Running, `kubectl describe node` 합계 |

### 4.2 ArgoCD 요청 950m, 실사용 9m

**문제.** 노드 CPU 요청이 70% 인데 실사용은 한참 아래였다.

**원인.**

```
              요청     실사용
controller    250m     4m
repo-server   250m     1m
server        250m     1m
applicationSet 100m    1m
redis         100m     2m
              ────     ──
              950m     9m
```

주석에 `t3.medium 최적화` 라고 적혀 있었다. 지금은 t3a.xlarge 다.

**개선.** 한도는 그대로 두고 요청만 내렸다. 동기화할 때만 오른다. `controller`
메모리만 올렸다. 요청 256Mi 에 281Mi 를 쓰고 있었다.

**결과.**

| | 전 | 후 |
|---|---|---|
| ArgoCD CPU 요청 | 950m | 275m |
| 노드 CPU 요청 | 2,800m (70%) | 2,135m (53%) |

| | |
|---|---|
| 조건 | `kubectl top`, 노드 전체. 2026-09-04. 4.1 과 날짜가 달라 합계가 다르다. 그 사이 모니터링 스택이 올라갔다 |
| 확인 | ArgoCD 파드 다섯 Running, 동기화 정상, `kubectl describe node` |

## 개선 5. CI 대기를 없앴다

### 5.1 응답 없는 저장소를 기다렸다

**문제.** CI 가 4분에서 11분이 됐다. `user-service` 잡 혼자 615초, 그중
`Build & Test` 가 484초. 로컬에서 같은 명령이 33초다.

**원인.** 로그 타임스탬프의 공백을 쟀다.

```
251.7초  Downloading from jboss-public-repository-group
187.3초  Downloading from jboss-public-repository-group
```

484초 중 439초가 저장소 응답 대기다. **거기서 받아온 아티팩트는 0개다.** 538개
전부 Central 에서 왔다. `keycloak-admin-client` 의 부모 pom 이 그 저장소를
선언하고 Maven 은 의존성 pom 이 선언한 저장소도 물려받아 찾는다.

**개선.** `.mvn/ci-settings.xml` 로 모든 저장소를 Central 로 미러링했다. CI 의
`mvn` 6곳에 `-s` 를 붙이고 Dockerfile 6개는 `/root/.m2/settings.xml` 로 복사한다.

**결과.**

| | 전 | 후 |
|---|---|---|
| Build & Test | 484초 | 47초 |
| 콜드 도커 빌드 | 427초 | 103초 |

| | |
|---|---|
| 조건 | GitHub Actions `user-service` 잡, 로그 타임스탬프 |
| 확인 | keycloak · jboss 캐시 지우고 다시 받아 테스트 204개 통과. JBoss 에만 있는 아티팩트 없음 |

경위는 [CI 가 11분인데 테스트는 45초였다](problem-solving.md#ci-가-11분인데-테스트는-45초였다).

### 5.2 같은 이미지를 두 번 스캔했다

**문제.** 리포 캐시 10GB 중 5.7GB 를 Trivy 가 차지하고 있었다. 그게 서비스당 264초를
아끼는 도커 레이어 캐시를 밀어냈다.

**원인.** 둘이다. 같은 이미지를 table 용과 SARIF 용으로 두 번 스캔했다. 스캔
14초에 바이너리 풀기와 DB 준비 15초가 붙어 30초가 중복이었다. 그리고 캐시가 일을
안 했다.

```
Cache restored successfully          954MB, 15초
[vulndb] Need to update DB           그러고 새로 받는다
```

날짜 키라 하루 954MB 씩 쌓였다.

**개선.** JSON 으로 한 번 받아 `trivy convert` 로 두 형식을 뽑는다. `convert` 는
0초다. 캐시는 껐다.

**결과.**

| | 전 | 후 |
|---|---|---|
| 서비스당 스캔 | 57초 | 33초 |
| Trivy 캐시 | 5.7GB | 0 |

| | |
|---|---|
| 조건 | GitHub Actions, 잡별 소요 |
| 확인 | 두 형식 산출물이 그대로 나오는지. SARIF 업로드 정상 |

경위는 [취약점 DB 캐시가 자리만 차지하고 있었다](problem-solving.md#취약점-db-캐시가-자리만-차지하고-있었다).

1. 히트와 미스의 차이가 "90% 개선" 으로 적혀 있었다. 조건을 붙이니 최적화가 아니었다.
   계산값으로 적어둔 188 KB 도 배포 뒤 재니 223 KB 였다.

2. 2,000회를 2회로 줄인 것이 캐시 계층을 얹은 것보다 컸다. 요청 수 → 응답 크기 →
   캐시 → 자원 순으로 봤고 앞쪽에서 큰 것이 나왔다.

3. 캐시 키를 일자로 쪼개니 히트율은 올랐고 왕복이 날짜 수만큼 늘었다. 그게 405 였다.

4. `limits / 2` 와 `t3.medium 최적화` 는 넣을 때 이유가 있었을 텐데 그 뒤로 아무도
   다시 안 봤다. 실사용을 재니 둘 다 달랐다.

5. CI 가 11분일 때 테스트는 45초였다. 나머지는 응답 없는 저장소를 기다린 시간이고
   로그 타임스탬프의 공백에 그대로 있었다.
