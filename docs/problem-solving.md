# 서비스

## 환율 조회가 500 을 냈다

`문제`
부하 테스트에서 `fx/latest` 를 46,350 번 부르는데 전부 실패였다. 컨트롤러에는
데이터가 없을 때 404 를 내는 분기가 있는데 거기까지 가지도 못했다.

겉으로는 정상으로 보였다. Resilience4j fallback 이 기본 환율을 돌려주고 있어서
화면에는 값이 떴다.

`원인`
Spring 캐시는 `Optional` 을 벗겨서 저장한다. 환율이 없으면 `Optional.empty()` 가
null 이 되고 캐시가 null 저장을 거부하면서 `IllegalArgumentException` 이 난다.

`해결`
`unless = "#result == null"` 로 null 이면 캐시하지 않게 했다.

그런데 이 수정을 절반만 검증했다. 고치고 404 가 나오는 것을 확인했는데 그때는
환율 데이터가 없는 상태였다. KoreaExim 실키로 262 건을 채우고 다시 보니 여전히 500 이었다.

```
SpelEvaluationException: Method isEmpty() cannot be found on type FxRate
```

처음 고칠 때 쓴 조건이 `#result == null || #result.isEmpty()` 였는데, `unless` 의
`#result` 도 `Optional` 이 벗겨진 뒤라 `FxRate` 다. 데이터가 없을 때는
`#result == null` 에서 단락 평가로 통과하고, 데이터가 생기면 뒤쪽을 평가하다 터진다.

빈 상태와 채워진 상태를 둘 다 봐야 검증이다. 한쪽만 보고 고쳤다고 넘어갈 뻔했다.

## 배당 한 건이 종목 전체를 깨뜨린다

`문제`
`YahooParser.createDividendDto` 에 NPE 가 나는 자리가 있었다. 배당 한 건이 깨지면
그 종목의 배당 파싱 전체가 예외로 끝난다.

`원인`
삼항 연산자가 `long` 과 `Long` 을 섞어 썼다.

```java
long timestamp = event.hasNonNull("date")
  ? event.get("date").asLong()      // long
  : parseLongSafely(eventKey);      // Long — 여기서 언박싱된다
```

자바는 삼항의 두 갈래 타입이 다르면 넓은 쪽으로 맞춘다. `Long` 이 `long` 으로
언박싱되므로 `parseLongSafely` 가 null 을 주면 그 자리에서 NPE 다. 바로 아래
null 체크는 도달하지 못하는 코드였다.

`해결`
양쪽을 `Long` 으로 맞췄다.

```java
Long timestamp = event.hasNonNull("date")
  ? Long.valueOf(event.get("date").asLong())
  : parseLongSafely(eventKey);
```

Yahoo 가 배당을 epoch 키로 주는 한 발동하지 않는다. 응답 모양이 바뀌면 조용히 죽는
자리였고 파서에 테스트를 붙이다 나왔다.

## 신규 상장이 하나도 안 들어왔다

`문제`
신규 상장 종목이 한 개도 추가되지 않고 있었다. 에러도 없었다.

`원인`
수집기가 기동할 때 종목이 하나라도 있으면 기존 종목 갱신만 하고 return 했다.
목록 조회 자체를 건너뛰니 초기 적재 이후로는 목록이 그대로 굳는다.
`기존 {}개 종목 발견 - 데이터 업데이트만 수행 (종목 추가 안 함)` 이라는 정상 로그를
남기면서 조용히 그랬다.

고치려고 목록 출처를 다시 보니 출처에도 문제가 있었다. NASDAQ 스크리너는 ETF 를
106 페이지로 나눠 주는데 받는 사이 목록이 재정렬돼 26% 가 중복이고 75% 만 남았다.
SPY 가 빠져 있던 게 그래서였다.

`해결`
두 가지를 같이 고쳤다.

목록 조회를 매일 도는 스케줄(평일 08:00)로 빼고, DB 에 없는 심볼만 추가하게 했다.
admin 화면에 수동 트리거도 붙였다.

출처는 AlphaVantage LISTING_STATUS 로 바꿨다. 호출 한 번에 CSV 로 전량이 오고,
`assetType` 과 `status` 를 필드로 준다. 이름으로 유형을 추측하거나 상장폐지를
따로 판정할 필요가 없어졌다. 호출은 108 회에서 1 회가 됐고 SPY 가 들어왔다.
SPY 는 실제 응답 행을 테스트에 고정해뒀다.

에러가 나는 장애보다 정상 로그를 남기며 안 하는 장애가 늦게 발견된다.
이건 모니터링이 아니라 사람이 알아채서 나왔다.

## 한국 시간 오전 9시 전에는 어제 날짜가 나왔다

`문제`
`getTodayString` 이 한국 자정부터 오전 9시 사이에 어제 날짜를 돌려줬다.
미국장 마감 직후에 쓰는 서비스라 그 시간대가 실사용 구간이다.

`원인`
`toISOString()` 은 UTC 로 변환한다. KST 는 UTC+9 이므로 오전 9시 전에는 날짜가 하루 밀린다.

`해결`
로컬 기준으로 계산하는 `toLocalDateString` 을 만들어 갈아끼웠다.

같은 계산이 `Trading.tsx` 에 복붙돼 있었고 유틸을 부르지 않았다. 유틸만 고치면
화면은 그대로 UTC 를 쓴다. 중복을 지우고 유틸로 모았다.

같은 로직이 몇 군데 있는지부터 셌어야 했다. 한 곳만 고치고 고쳤다고 착각할 뻔했다.

<br>

## 로그인이 가입 여부를 알려줬다

`문제`
보안 점검에서 나왔다. 로그인만 쳐도 그 이메일이 가입돼 있는지 알 수 있었다.

```
없는 계정        401  "이메일 또는 비밀번호가 올바르지 않습니다"
가입된 계정      400  "이메일 인증이 완료되지 않았습니다"    ← 비번을 몰라도 나온다
```

`원인`
로그인이 이메일 인증 여부를 비밀번호 검증보다 **먼저** 봤다. 그래서 비번이 틀려도
"이 계정은 존재하고 인증만 안 됐다" 가 응답으로 나갔다.

`해결`
비밀번호 검증을 앞으로 옮겼다. 이제 비번을 통과한 사람에게만 미인증 안내가 간다.
틀리면 가입 여부와 무관하게 401 이다.

남은 구멍이 있다. 없는 계정은 BCrypt 대조를 타지 않아 응답 시간 차이로는 여전히
구분된다. 막으려면 없는 계정에도 더미 해시 대조를 한 번 태워야 하는데 지금 규모에는
과하다고 보고 두었다.

<br>

## 운영이 자신을 dev 로 알았다

`문제`
보안 점검에서 나왔다. 운영에 깨진 JSON 을 보내니 에러 응답에 예외 클래스 이름과
상세 메시지가 그대로 내려왔다. 개발 환경에서만 보여야 하는 정보다.

`원인`
개발 환경 판정이 이렇게 돼 있었다.

```java
String profile = System.getProperty("spring.profiles.active", "dev");
```

프로파일은 환경변수 `SPRING_PROFILES_ACTIVE` 로 주입한다. `System.getProperty` 는
JVM 시스템 프로퍼티를 읽는 것이라 환경변수가 안 잡히고, 기본값 `"dev"` 로 떨어진다.
운영이 스스로를 개발이라고 판정하고 있었다.

`해결`
Spring 이 실제로 활성화한 프로파일을 본다.

```java
for (String profile : environment.getActiveProfiles()) { ... }
```

배포 후 운영에서 같은 요청으로 확인했다. 이제 `MALFORMED_REQUEST_BODY` 한 줄의
400 만 내려온다.

기본값이 "안전한 쪽" 이 아니었다는 게 핵심이다. 판정이 실패하면 dev 로 간주하니
실패가 곧 정보 노출이었다. 기본값은 잠그는 쪽이어야 한다.

이때는 점검 대상이던 user-service 만 고쳤다. 나중에 훑어보니 같은 판정 코드가
backtest 와 trade 에 복붙돼 있었다. 서킷브레이커 때와 같은 결말 — 한 곳을 고치면
같은 로직이 몇 군데 있는지부터 세야 한다.

## 서킷브레이커가 한 번도 열리지 않았다

`문제`
`fx/latest` 가 500 을 46,350 번 냈는데 서킷브레이커 실패율이 0 이었다. 서킷은 끝까지
닫혀 있었다.

`원인`
`recordExceptions` 에 `HttpServerErrorException` 이 적혀 있었다. 이건 RestTemplate 이
던지는 예외다. 호출은 Feign 으로 하므로 `FeignException` 계열이 나온다.
나열된 것만 실패로 세기 때문에 500 을 아무리 받아도 실패가 아니었다.

`해결`
고치는 데 두 번 틀렸다.

| 값 | 결과 |
|---|---|
| `HttpServerErrorException` | Feign 예외를 못 잡아 서킷이 안 열린다 |
| `FeignException$ServerError` | 그런 클래스가 없다. **기동 자체가 실패** |
| `FeignException$FeignServerException` | 정상 |

`ServerError` 나 `ClientError` 라는 이름은 없다. 5xx 부모는 `FeignServerException`,
4xx 부모는 `FeignClientException` 이다.

설정 문자열이라 컴파일러가 잡아주지 않는다. Resilience4j 가 문자열을 Class 로 변환하는
시점에 `ClassNotFoundException` 이 나고 그게 설정 오류로 보고되며 애플리케이션이 뜨지
않는다. **설정 리포는 컴파일 단계가 없어서 코드보다 위험하다.** 두 번째 값을 확인 없이
푸시했다가 서비스를 세웠다.

검증은 market-data 를 내렸다 올리며 했다.

| 단계 | 서킷 | 응답 |
|---|---|---|
| 기동 직후 | CLOSED | — |
| market-data 중지 후 8회 | **OPEN** | 404 (fallback) |
| market-data 복구 후 5회 | **CLOSED** | 200 |

상태는 `resilience4j_circuitbreaker_state` 메트릭으로 봤다. actuator health 는
`show-details` 가 없어 상태가 보이지 않는다.

뒤에 다른 서비스를 훑어보니 같은 병이 두 군데 더 있었다. user-service 는 예외 목록이
그대로 RestTemplate 것이었고, trade-service 는 거기에 더해 설정의 인스턴스 이름이
`marketDataService` 인데 코드는 `marketService` 라 설정 자체가 붙지 않았다.
이름이 어긋난 서킷은 기본값으로 도는데, 기본 `minimumNumberOfCalls` 가 100 이라
사실상 열리지 않는다. backtest 만 고치고 같은 로직이 몇 군데 있는지 안 센 결과다.

## 백테스트 5년치가 100초 걸렸다

`문제`
백테스트를 5년치로 돌리면 100초가 걸리고 500 이 자주 났다. 1년치는 정상이었다.
Tempo 는 span 2,000 개를 받다 OOMKilled 됐다.

그때 기록에는 서킷브레이커가 열렸다고 적었다. 나중에 부하 테스트에서 확인해보니
예외 목록 문제로 서킷은 열릴 수 없는 상태였다(아래 서킷브레이커 항목). 열렸다고
믿은 것이지 확인한 것이 아니었다.

`원인`
범위를 늘렸을 때만 나는 문제라 데이터부터 의심했다. 5년치 데이터는 DB 에 있었고
slow query 로그도 50ms 안쪽으로 정상이었다.

market-data-service 로그를 보고서야 보였다. **API 호출이 2,000 번**이었다.

전략 실행 루프가 하루씩 돌면서 매일 가격과 환율을 개별로 불렀다.
5년이면 약 1,800 일, 가격과 환율을 합쳐 2,000 회다.

`해결`
범위를 한 번에 받는 Bulk API 를 만들었다.

```
호출  2,000 회 → 2 회
시간    100 초 → 1.5 초
```

배운 것은 두 가지다.

1년치로만 테스트해서 5년치 문제를 못 찾았다. 실제로 쓰는 범위로 테스트해야 한다.
기능이 되는지만 보면 규모에서 나는 문제는 안 보인다.

범위 조회가 필요할 거라는 걸 예상하지 못했다. 단건 API 를 먼저 만들고 루프로 때웠다.

## 요청 하나가 10.7 배로 증폭됐다

> 위의 N+1 과 같은 병이 다른 자리에서 재발한 것이다. 그때는 루프 안의 개별 호출이었고
> 이번에는 값이 하나뿐인 환율을 종목마다 불렀다. 고친 방식도 같다 —
> 호출 횟수를 세어 보고서야 보였다.

`문제`
부하 테스트 중 서비스별 요청률을 보니 안쪽이 훨씬 바빴다.

```
게이트웨이      208 rps    사용자 요청
backtest        207 rps    그대로 전달
market-data   2,216 rps    10.7 배
```

`원인`
엔드포인트별로 나누니 종목 분석 한 건이 market-data 를 6.4 회 불렀다.
그중 `fx/latest` 는 값이 하나뿐인데 종목마다 부르고 있었다.

`해결`
`MarketDataClientWrapper` 에 60 초 캐시를 뒀다. 백테스트 다섯 번에 한 번만 나간다.

팬아웃 자체는 마이크로서비스의 정상 동작이다. 문제는 같은 값을 반복해서 부르는 것이었고
그건 호출 횟수를 세어 보고서야 보였다.

# 게이트웨이

## 타임아웃인데 405 가 나왔다

`문제`
백테스트 API 가 **405 Method Not Allowed** 를 냈다. 장기간 조회(2년 이상)에서만 나고
단기간은 정상이었다.

POST 로 부르는 게 맞는데 405 가 나온다. 게다가 즉시가 아니라 3~5초 뒤에 나왔다.

`원인`
405 면 라우팅 문제라고 보고 인프라부터 뒤졌다. 여섯 개를 배제했다.

| 가설 | 결과 |
|---|---|
| Cloudflare Tunnel | 정상 |
| Traefik Ingress 라우팅 | 정상 |
| Gateway 라우팅 설정 | 타임아웃 발견 |
| DB 쿼리 지연 | slow query 정상 |
| Redis 연결 | 정상 |
| 네트워크 | 정상 |
| **코드 레벨 병목** | **캐시 조회 루프에서 4.5초** |

병목은 범위 조회가 날짜별로 캐시를 개별 조회하는 코드였다. 2년치면 약 700 번 루프를 돈다.
캐시 히트여도 700 번 네트워크 왕복이 생긴다.

이 루프는 캐시 히트율을 올리려다 넣었다. 처음에는 기간 단위로 캐시했는데
요청 범위가 조금만 달라도 키가 어긋나 히트가 거의 없었다. 일자별로 쪼개니 겹치는 날짜가
재사용되면서 히트율은 올랐고 대신 범위 조회가 날짜 수만큼 왕복하게 됐다.
한쪽을 고치면서 다른 쪽을 망가뜨렸다.

여기서 한 번 잘못 닫을 뻔했다. TimeLimiter 시간을 늘리니 405 가 안 났다. 해결한 줄 알았다.
그런데 타임아웃이면 504 여야지 왜 405 인지가 설명되지 않았다. 그게 걸려서 계속 팠다.

두 겹이었다.

첫째, 타임아웃이 나면 게이트웨이는 504 를 주는 게 아니라 `fallbackUri: forward:/fallback`
으로 넘긴다. 넘겨받을 `FallbackController` 가 없었다. 405 는 게이트웨이가 아니라
그 forward 가 낸 것이다.

둘째, 컨트롤러를 만들었는데 또 405 였다. `@GetMapping` 으로 만들어서 POST 를 못 받았다.
`@RequestMapping` 으로 바꾸고서야 끝났다.

`해결`
캐시 루프를 걷어내 4.5 초를 0.6 초로 줄이고, `FallbackController` 를 `@RequestMapping`
으로 만들었다.

**증상이 사라진 것과 해결한 것은 다르다.** 성능을 고쳐 405 가 안 나오게 된 시점에 멈췄다면
fallback 경로는 여전히 비어 있었을 것이다. 다음에 어떤 이유로든 타임아웃이 나면 같은 405 가
다시 나온다.

405 는 대개 HTTP 메서드 문제지만 이번엔 아니었다. 에러 코드를 그대로 믿을 게 아니었다.
"즉시 나는 405" 와 "3~5초 뒤에 나는 405" 는 다른 사건이다.

<br>

## 처리량 상한이 앱이 아니라 게이트웨이였다

`문제`
k6 로 램프 부하를 걸었더니 실패율이 89.87% 였다. 그런데 응답 시간이 p95 12ms 로 멀쩡했다.

`원인`
빠르게 거절당하고 있었다. 느려서 실패하는 쪽이 아니었다.
상태 코드를 집계하니 87% 가 429 였다.

게이트웨이 설정이 `replenishRate: 200` 이었고 측정된 통과량 202 rps 와 일치했다.
상한은 rate limiter 였다. 앱 쪽이 아니었다.

게이트웨이를 우회해 서비스를 직접 때리니 3,350 rps 가 나왔다.

| 구간 | 처리량 | p95 | 5xx |
|---|---|---|---|
| 게이트웨이 경유 | 202 rps | 28.8ms | 0 |
| 우회 (50 VU) | 3,368 rps | 29.8ms | 0 |
| 우회 (250 VU) | 3,339 rps | 177ms | 0 |

`해결`
값을 바꾸지 않았다. 앱의 실제 한계를 모르는 상태에서 문을 넓히면 병목을
게이트웨이에서 앱으로 옮기는 것에 그친다.

게다가 3,350 rps 도 앱의 한계가 아니다. 그 시점에 market-data 프로세스 CPU 는 38.7%
인데 호스트 전체는 67.8% 였다. 포화한 쪽은 측정 환경이었다. 앱이 아니었다. 부하 생성기를
같은 PC 에서 돌린 한계다.

그래서 순서를 정하고 문서에 남겼다. 앱 한계 측정 → 적정값 산정 → X-Forwarded-For 처리.

k6 스크립트에서 429 를 5xx 와 분리해 세게 바꿨다. 실패로 뭉치면 부하를 올릴수록
실패율만 오르고 앱의 한계는 영영 안 보인다.

<br>

## rate limit 이 IP 별이 아니라 전체로 걸렸다

`문제`
위 부하 테스트를 파고들다 나왔다. 버킷 단위를 정하는 `ipKeyResolver` 가 이렇게 돼 있었다.

```java
String clientIp = exchange.getRequest().getRemoteAddress().getAddress().getHostAddress();
```

`원인`
`getRemoteAddress()` 는 직전 홉의 주소다. 운영은 Traefik IngressRoute 가 앞에 있어서
게이트웨이 눈에는 모든 요청이 Traefik 파드 IP 하나로 보인다.

의도는 "IP 하나당 200/s" 인데 실제로는 "전체 합쳐서 200/s" 다. Redis 기반이라 게이트웨이
파드를 늘려도 합은 그대로다. 스케일아웃이 처리량을 늘리지 못한다.

로컬에서는 k6 나 브라우저가 게이트웨이에 직접 붙어 실제 IP 가 보이므로 정상 동작한다.
운영에서만 나타나는 종류다.

`해결`
당장은 고치지 않고 순서를 지키기로 했다. 버킷을 IP 별로 쪼개면 전체 통과량이 늘고
그만큼 앱 부하가 커진다. 앱이 감당하는지 모르는 상태에서 문을 넓히는 셈이다.

나중에 보안 점검에서 로그인 무차별 대입이 안 막히는 게 나오면서 순서를 어기고 먼저 고쳤다.
무차별 대입 방어가 IP 별 버킷을 전제하기 때문이다.

```java
XForwardedRemoteAddressResolver.maxTrustedIndex(1)
```

프록시 한 대까지 신뢰해 그 앞의 XFF 값을 실 클라이언트 IP 로 쓴다. 클라이언트가 임의로
넣은 앞부분은 무시되므로 스푸핑으로 버킷을 회피할 수 없다.

대신 원래 하려던 1·2 단계가 남았다. 지금 다른 라우트는 여전히 200/s 인데 버킷만
쪼개져서 전체 통과량이 늘어난 상태다. 앱 한계를 재고 값을 다시 잡아야 닫히는 항목이다.

## 로그인 한 번이 다른 라우트의 토큰을 깎았다

`문제`
E2E 스위트가 열 번에 한두 번 429 로 깨졌다. 재현이 잘 안 돼 타이밍 문제로 보였다.
실패 응답 헤더를 남기게 하고 반복하니 이렇게 나왔다.

```
x-ratelimit-remaining: 0
x-ratelimit-burst-capacity: 1000
```

용량 1000 인 버킷이 0 이다. 스위트는 1000 번을 부르지 않는다.

`원인`
버킷 키에 라우트가 없었다. Redis 키가 `request_rate_limiter.{IP}.tokens` 하나뿐이라
모든 라우트가 그것을 나눠 쓴다.

그런데 라우트마다 상한이 다르다.

```
user-login-route   replenishRate 1    burstCapacity 30    requestedTokens 10
backtest-route     replenishRate 500  burstCapacity 1000  requestedTokens 1
```

Spring 의 Lua 스크립트는 저장된 토큰 수를 **호출한 라우트의 burstCapacity 로 자른다.**
로그인이 지나가는 순간 버킷이 30 이하로 잘리고, 직후에 들어온 백테스트 요청은 0 을 만난다.

실측이 분명했다. 시장 조회로 채워 395 였던 버킷이 로그인 한 번에 20 이 됐다.
385 가 아니라 20 이다. 365 개가 증발한다.

`해결`
키에 라우트 ID 를 넣어 버킷을 갈랐다.

```java
Route route = exchange.getAttribute(ServerWebExchangeUtils.GATEWAY_ROUTE_ATTR);
return Mono.just(clientIp(exchange) + ":" + routeId(exchange));
```

```
{IP:market-data-route} = 395   로그인에 안 깎임
{IP:user-login-route}  = 20
```

고치기 전 8회 중 2회가 깨졌고, 고친 뒤 클린룸 포함 15회 연속 통과한다.

곁가지로 같은 파일의 NPE 두 곳을 막았다. 미해석 `InetSocketAddress` 는 `getAddress()` 가
null 이고 끊긴 커넥션은 `getRemoteAddress()` 자체가 null 인데 `requireNonNull` 로
감싸여 있어 그 경우 500 이 나갔다.

# 빌드와 CI

## CI 배지는 초록인데 테스트가 안 돌았다

`문제`
CI 워크플로에 서비스 두 개만 `-DskipTests` 로 도는 분기가 있었다. 배지는 통과로 표시됐다.

`원인`
왜 스킵했는지부터 확인했다. 두 서비스를 각각 돌려보니 갈렸다.

- `user-service` — 203 개 전부 통과. 스킵할 이유가 없었다
- `market-data-service` — 통합테스트 14 개가 컨텍스트 로딩부터 실패

market-data 의 실패는 테스트 코드 문제가 아니었다. `FxRateService` 구현체 둘 다
`@ConditionalOnProperty(marketdata.provider)` 가 붙어 있는데 `application-test.yml` 에
그 값이 없었다. 빈이 하나도 안 뜨니 컨텍스트가 실패한다.

값을 넣으니 다음 단계에서 `spring.kafka.bootstrap-servers` 플레이스홀더가 걸렸다.
테스트 설정이 운영 설정을 따라가지 못한 상태였다.

`해결`
테스트 설정에 두 줄을 추가하고 CI 의 분기를 없앴다. 여섯 서비스가 같은 명령을 탄다.

스킵은 대개 "지금 안 되니까 나중에" 로 들어간다. 그 나중이 오지 않으면 배지가 거짓말을
하기 시작한다. 스킵할 거면 왜 스킵하는지를 같이 적어야 한다.

<br>

## BOM 을 import 했는데 라이브러리가 안 왔다

`문제`
분산 추적을 붙였는데 게이트웨이 스팬이 하나도 없었다. 다른 서비스는 정상이고
메트릭도 정상 수집됐다.

`원인`
첫 가설은 WebFlux 였다. 게이트웨이만 리액티브 스택이고 리액티브에서는 요청이 여러
스레드를 옮겨다녀 `ThreadLocal` 기반 컨텍스트 전파가 끊기기 쉽다. 게이트웨이는 프록시라
헤더 전달까지 얽힌다.

이 가설은 틀렸다. `mvn dependency:tree` 로 확인하니 추적 라이브러리 자체가
클래스패스에 없었다.

`ggeolmuse-bom` 한 파일이 `dependencyManagement`(버전) 와 `dependencies`(라이브러리) 를
겸하는데 `<scope>import</scope>` 로 가져오면 앞쪽만 온다. Maven 스펙이다. 라이브러리까지
받으려면 BOM 을 일반 의존성으로 한 번 더 선언해야 하고, 여섯 중 넷만 그렇게 하고 있었다.

`management.tracing.*` 설정은 읽히지만 스팬을 만들 구현체가 없어 조용히 무시된다.
에러 로그가 남지 않아 설정만 봐서는 알 수 없었다.

`해결`
BOM 을 통째로 넣을 수는 없었다. BOM 의 `dependencies` 에 `spring-boot-starter-web` 과
`data-jpa` 가 있어서 WebFlux 게이트웨이가 서블릿으로 바뀌고 DataSource 자동설정에 걸린다.
필요한 두 개만 직접 선언하고 그 이유를 pom 주석에 남겼다. 나중에 "다른 서비스처럼
통일하자" 고 BOM 을 통째로 넣으면 기동이 깨진다.

`gateway-server → market-data-service` 가 하나의 트레이스로 이어지는 것을 확인했다.
의존성 두 줄이었다.

WebFlux 컨텍스트 전파는 Spring Boot 3.x + Reactor 3.5 조합에서 이미 자동으로 처리되고
있었다. 옛 버전의 문제를 현재 버전에 그대로 적용한 오진이었다.

<br>

## CI 가 11분인데 테스트는 45초였다

`문제`
CI 가 4분에서 11분으로 늘었다. 잡별로 보니 `user-service` 혼자 615초고 나머지는
100~163초다. 그중 `Build & Test` 가 484초였다.

로컬에서 같은 명령이 33초다. 14배 차이를 테스트가 설명하지 못한다.

`원인`
로그 타임스탬프의 공백을 재보니 답이 나왔다.

```
251.7초  Downloading from jboss-public-repository-group: ...
187.3초  Downloading from jboss-public-repository-group: ...
```

484초 중 439초가 저장소 응답 대기다. 그리고 **거기서 받아온 아티팩트는 0개**다.
538개 전부 Central 에서 왔다.

`keycloak-admin-client` 의 부모 pom 이 그 저장소를 선언한다. Maven 은 내 pom 의
저장소만 보는 게 아니라 의존성 pom 이 선언한 것도 물려받아 뒤진다. keycloak 을 쓰는
서비스가 user-service 뿐이라 다른 다섯은 해당이 없었다.

로컬에서 안 보인 이유는 `~/.m2` 가 그 저장소를 이미 죽은 걸로 알고 넘어가서다.

`해결`
`.mvn/ci-settings.xml` 로 모든 저장소를 Central 로 미러링했다.
Maven 이 `.mvn` 의 settings 를 자동으로 읽지 않아 CI 의 mvn 호출 6곳에 `-s` 를 붙이고
Dockerfile 6개는 `/root/.m2/settings.xml` 로 복사한다.

|---|---|---|
| Build & Test | 484초 | 47초 |
| 콜드 도커 빌드 | 427초 | 103초 |

## 메모리가 부족해 인스턴스를 키우려 했다

`문제`
t3.xlarge(16GB) 에서도 메모리가 부족했다. 서비스를 여섯 개 띄우면 여유가 없었다.

`원인`
인스턴스를 키우기 전에 실제 사용량부터 쟀다. Actuator 메트릭으로 서비스별 힙 사용량을
뽑아보니 할당량과 차이가 컸다.

```
user-service   실제 151MB  /  할당 768MB
trade-service  실제 150MB  /  할당 768MB
gateway         실제  75MB  /  할당 384MB
```

`-Xmx` 미설정이었다. JVM 은 값이 없으면 컨테이너 메모리의 25% 를 기본으로 잡는다.
컨테이너 한도를 넉넉히 준 것이 그대로 힙 기본값을 밀어올렸다.

"메모리가 부족하다" 의 원인이 트래픽이나 누수가 아니라 **설정 부재**였다.

`해결`
실측값에 여유를 얹어 서비스별로 `-Xmx` 를 명시했다.

| 서비스 | 기존 | 변경 |
|---|---|---|
| market-data | 1024m | 768m |
| user-service | 768m | 256m |
| trade-service | 768m | 256m |
| backtest | 640m | 320m |
| gateway | 384m | 192m |
| config-server | 256m | 128m |

t3.xlarge → t3.large 로 내렸다. 월 $92 절감.

## 배포할 때마다 서버가 응답 불능이 됐다

`문제`
`helm upgrade` 를 실행하면 EC2 가 응답하지 않았다. 배포 순간에만 생기고 평시에는 멀쩡했다.

`원인`
Kubernetes 롤링 업데이트의 기본값이 `maxSurge: 25%` 다. 기존 파드를 유지한 채로 새 파드를
먼저 띄운다. 무중단 배포를 위한 기본값인데, 단일 노드에서 서비스 여섯 개가 도는 환경에서는
순간 메모리가 두 배 가까이 필요해진다.

노드에 그만한 여유가 없었다. 무중단을 위한 설정이 오히려 전체를 멈춰 세웠다.

`해결`
무중단을 포기하고 순차 교체로 바꿨다.

```yaml
rollingUpdate:
  maxSurge: 0        # 새 파드를 먼저 띄우지 않는다
  maxUnavailable: 1  # 기존 파드를 하나 내리고 새로 띄운다
```

배포 중 응답 불능이 사라졌다. 대신 서비스별로 수 초의 다운타임이 생긴다.
개인 프로젝트의 트래픽 규모상 받아들일 수 있는 교환이었다.

게이트웨이만 예외로 `maxSurge: 1` 을 유지한다.

## ingress 를 붙였는데 외부에서 안 닿았다

`문제`
EC2 에 k3s 를 올리고 서비스를 띄웠는데 외부에서 접속이 안 됐다. 파드는 전부 Running 이고
클러스터 안에서는 서로 통신이 됐다.

`원인`
ingress 컨트롤러로 nginx-ingress 를 설치했다. 쿠버네티스에서 가장 많이 쓰는 것이라
당연히 그걸 넣었다.

**k3s 는 Traefik 을 기본으로 내장한다.** 설치하면 Traefik 이 이미 떠서 80·443 을 잡고 있다.
그 위에 nginx-ingress 를 얹으니 둘이 같은 자리를 두고 부딪혔고 트래픽이 어디로도
제대로 흐르지 않았다.

`해결`

그 사이 커밋이 일곱 개다.

지금 `helm/ggeolmuse/templates/infrastructure/ingress-controller.yaml` 에 nginx-ingress
템플릿이 남아 있지만 prod 는 `ingressController.enabled: false` 라 렌더되지 않는다.
`aws-deploy/k3s/02-install-nginx-ingress.sh` 도 그때의 잔재다.

"쿠버네티스에서는 보통 nginx-ingress" 라는 일반론을 k3s 에 그대로 가져간 것이 원인이었다.
배포판이 무엇을 이미 갖고 있는지부터 봤어야 했다. 경량 배포판은 기본 구성이 다르다.

## 새 서비스만 503 이 났다

`문제`
FastAPI 로 만든 chat-service 를 붙였는데 웹에서 부르면 실패했다. 증상이 단계마다 달라서
원인을 세 번 잘못 짚었다.

| 시점 | 응답 | 실제 원인 |
|---|---|---|
| 최초 | 404 | 프론트가 `/api/api/chat` 으로 호출 (경로 중복) |
| 프론트 수정 후 | 503 | NetworkPolicy 가 8000 포트를 막음 |
| netpol 수정 후 | 401 | 테스트에 쓴 JWT 만료 (정상 동작) |

`원인`
503 은 게이트웨이 CircuitBreaker 의 fallback 이었다. 그런데 chat-service 로그에
`/api/chat` 요청이 **한 건도 안 찍혔다.** 게이트웨이가 forward 를 시도조차 못 했다.

임시 curl 파드를 띄워 클러스터 내부에서 각 서비스를 때려봤다.

```
user:000   ← 연결 실패
gw:404     ← 연결은 됨 (경로만 틀림)
chat:000   ← 연결 실패
```

게이트웨이는 닿고 백엔드는 안 닿는다. NetworkPolicy 를 확인하니 허용 포트가
8080~8083 뿐이었다. 기존 서비스가 전부 Spring Boot 라 그 범위만 열려 있었고
FastAPI 인 chat-service 만 8000 을 쓴다.

chat-service 파드는 `tier: business-service` 라벨이 있어 정책 적용 대상에는
들어갔는데 허용 포트에 8000 이 없어 모든 ingress 가 차단됐다.

> 라벨을 붙였기 때문에 오히려 막혔다. 라벨이 없었다면 정책 대상이 아니라 통과했을 것이다.

`해결`
Helm values 의 `networkPolicy.ports` 에 8000 을 추가했다. base 와 prod 양쪽 다 고쳐야 한다.
ArgoCD 가 차트를 추적하므로 `kubectl edit` 으로 직접 고치면 self-heal 로 되돌아간다.

두 가지를 배웠다.

상태 코드가 계층을 알려준다. 404 는 라우트가 없는 것, 503 은 라우트는 있는데 백엔드에
못 닿는 것, 401 은 끝까지 도달했고 인증만 걸린 것이다. 503 이 401 로 바뀐 순간이
뚫렸다는 신호였다.

**백엔드 로그에 요청이 안 찍히면 앱 문제가 아니다.** 그 시점에서 앱 디버깅을 접고
네트워크 계층으로 갔어야 했다.

<br>

# 로컬 개발 환경

## 모든 AWS 명령이 빈 응답을 냈다

`문제`
EC2 스케줄러를 terraform 으로 올리려는데 AWS CLI 가 통째로 안 됐다.

```
$ aws sts get-caller-identity
Unable to parse response (no element found: line 1, column 0), invalid XML received.
b''
```

모든 서비스에서 같았다. PowerShell / Git Bash 둘 다, 재부팅해도 그대로였다.

`원인`
빈 응답이라 네트워크 계층으로 판단하고 한참 헤맸다. 프록시(환경변수·WinHTTP·WinINET·WPAD),
endpoint override, hosts 파일, DNS, 보안 모듈까지 여덟 가지를 봤고 **전부 정상**이었다.

오해를 부른 건 `curl` 이었다. STS 를 직접 때리면 정상 응답이 왔다.

```
curl.exe -sv https://sts.ap-northeast-2.amazonaws.com
# HTTP/1.1 302 Found
# x-amzn-RequestId: a362c356-...   ← AWS 가 준 응답이 맞다
```

"curl 은 되는데 python 만 안 된다 → 프로세스 단위로 트래픽을 가로채는 무언가가 있다" 는
결론으로 갔고 LSP / WFP 필터 드라이버를 뒤지기 시작했다. 완전히 틀린 방향이었다.

우회하려고 terraform 을 돌렸더니 전혀 다른 메시지가 나왔다.

```
retrieving caller identity from STS: operation error STS: GetCallerIdentity,
decomposing request: net/http: invalid header field value for "Authorization"
```

Go 의 `net/http` 는 헤더에 허용되지 않는 문자가 있으면 전송 전에 거부한다.
`Authorization` 헤더는 자격증명으로 만들어지므로 → credentials 파일이 오염됐다.

값을 노출하지 않고 확인했다.

```
len=9   nonascii_or_ctrl=
len=41  nonascii_or_ctrl=22   ← 범인
len=64  nonascii_or_ctrl=
```

`aws_access_key_id` 줄에 제어문자 22(0x16, SYN) 가 섞여 있었다. 눈으로는 안 보인다.
정상은 `aws_access_key_id = `(20자) + 키 20자 = 40 인데 41 이었다. 키가 21자로 인식되면서
SigV4 서명이 깨졌다.

`해결`
ASCII 출력 가능 문자만 남겼다. 키 재발급은 필요 없었다.

도구마다 증상이 달랐던 이유가 핵심이다.

| 도구 | Authorization 헤더 | 결과 |
|---|---|---|
| `curl` (수동 요청) | **없음** (미서명) | AWS 가 정상 응답 → "네트워크 정상" 으로 오판 |
| aws-cli (Python) | 오염된 값으로 생성 | 요청이 깨져 빈 응답. 원인이 안 보인다 |
| terraform (Go) | 오염된 값으로 생성 | 전송 전 검증에서 거부 → **원인 명시** |

curl 이 성공한 건 자격증명을 아예 안 썼기 때문이었다. 네트워크가 정상이어서가 아니다.
"A 는 되는데 B 는 안 된다" 를 비교하려면 A 와 B 의 조건이 같아야 한다. 조건이 달랐으므로
"네트워크는 정상" 이라는 결론 자체가 성립하지 않았다.

에러 메시지가 불친절하면 다른 런타임으로 같은 일을 시켜본다. botocore 는 `b''` 만 뱉었지만
terraform 은 무엇이 잘못됐는지 정확히 알려줬다.
