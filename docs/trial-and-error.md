근거를 갖고 정한 것들이 확인해보니 반대인 경우가 여럿이었다.
믿었던 것과 갈린 근거를 남긴다.

장애를 어떻게 고쳤는지는 [문제 해결](problem-solving.md) 에 따로 있다.
여기는 판단이 틀린 이야기만 모았다. 단순히 빠뜨린 것은 넣지 않았다.

확인 방법은 항목마다 다르다. 하나로 통일된 지표가 없어서 무엇으로 갈렸는지를
항목마다 적었다. 절마다 첫 줄에 날짜와 그 뒤로 바뀐 것을 뒀다. 날짜는 고친 커밋
기준이고 없는 건 없다고 적었다.

```

Actuator 메트릭         서비스별 실제 힙 사용량
mvn dependency:tree     클래스패스에 실제로 있는 것
클러스터 내부 curl 파드  어디까지 닿는지
라이브 요청             인증·인가를 실제로 쳐서
git 이력                무엇을 몇 번 고쳤는지
```

## k3s 에는 Traefik 이 이미 있었다

`날짜` 2025-11-05 · `그 뒤로` Traefik IngressRoute 로 운영. nginx 템플릿은 prod 에서 비활성

EC2 에 k3s 를 올리고 ingress 컨트롤러로 nginx-ingress 를 설치했다. 쿠버네티스에서
가장 많이 쓰는 것이니 당연하게 여겼다.

파드는 전부 Running 이고 클러스터 안에서는 통신이 되는데 외부에서 안 닿았다.

k3s 는 Traefik 을 기본으로 내장한다. 설치 시점에 이미 Traefik 이 떠서 80·443 을
잡고 있다. 그 위에 nginx-ingress 를 얹으니 같은 자리를 두고 부딪혔다.

Traefik 으로 갈아타고 IngressRoute 로 라우팅을 다시 짜는 데 사흘이 걸렸다.
git 이력에 2025-11-05 부터 11-07 까지 커밋 일곱 개가 남아 있다.

일반론을 배포판에 그대로 가져간 것이 원인이었다. k3s 에는 Traefik 이 이미 있었다.

## 405 는 타임아웃이었다

`날짜` 2025-10-15 · `그 뒤로` FallbackController 를 @RequestMapping 으로, 캐시 루프 제거. 메서드 다섯을 테스트로 고정

백테스트 API 가 405 를 냈다. 405 는 HTTP 메서드 문제이니 라우팅 어딘가로 짐작하고
인프라부터 뒤졌다. Cloudflare Tunnel, Traefik Ingress, Gateway 라우팅 설정, DB,
Redis, 네트워크까지 여섯 개를 배제했다.

전부 정상이었다.

실제 원인은 **타임아웃**이었다. Spring Cloud Gateway 는 TimeLimiter 타임아웃 때
HTTP 1.1 연결을 강제 종료하면서 405 를 반환한다. 504 가 아니다.

단서는 처음부터 있었다. 405 가 즉시가 아니라 3~5초 뒤에 나왔다.
클라이언트가 메서드를 잘못 쓴 405 는 즉시 나온다. 시간이 걸린다는 건 서버가
무언가를 하다 실패했다는 뜻이었는데 상태 코드만 보고 그 차이를 흘렸다.

같은 405 라도 즉시 나는 것과 3~5초 뒤에 나는 것은 다른 사건이었다.

<br>

## fallback 경로는 비어 있었다

`날짜` 2025-10-15 · `그 뒤로` fallback 경로까지 채움. 같은 405 건

위 405 를 파다가 캐시 조회 루프가 4.5초를 먹는 걸 찾았다. TimeLimiter 시간을 늘리니
405 가 안 났다. 해결됐다고 정리했다.

그런데 하나가 설명되지 않았다. 타임아웃이면 504 여야지 왜 405 인가.
그게 걸려서 계속 팠고 두 겹이 더 나왔다.

`fallbackUri: forward:/fallback` 설정은 있는데 받을 `FallbackController` 가 없었다.
만들었더니 또 405 였다. `@GetMapping` 이라 POST 를 못 받았다. `@RequestMapping` 으로
바꾸고서야 끝났다.

성능을 고친 시점에 멈췄다면 fallback 경로는 비어 있는 채로 남았을 것이다. 다음에
어떤 이유로든 타임아웃이 나면 같은 405 가 다시 나온다.

## 5년치는 API 를 2,000 번 불렀다

`날짜` 기록 없음 · `그 뒤로` 범위를 한 번에 받는 Bulk API

백테스트를 만들며 1년치로 테스트했다. 잘 돌았고, 1년치로 되면 5년치도 될 거라 봤다.

5년치를 돌리니 100초가 걸리고 500 이 났다. 데이터를 의심했는데 DB 에 있었고 쿼리도
50ms 안쪽이었다. market-data 로그를 보고서야 **API 호출이 2,000 번**인 걸 알았다.

전략 실행 루프가 하루씩 돌며 가격과 환율을 개별로 불렀다. 1년이면 약 400 회라
느리긴 해도 넘어갔고 5년이 되니 무너졌다.

1년치로만 테스트해서 5년치 문제를 못 봤다.
그리고 범위 조회가 필요할 거라는 걸 처음에 예상하지 못해 단건 API 를 먼저 만들고
루프로 때운 것이 시작이었다.

## 기간 단위 캐시는 히트가 없었다

`날짜` 기록 없음 · `그 뒤로` 일자별 캐시는 유지, 범위 조회 루프는 제거해 0.6초

조회가 기간 단위이니 캐시도 기간 단위로 걸었다. 자연스러운 선택 같았다.

히트가 거의 없었다. 요청 범위가 조금만 달라도 키가 어긋난다. 2024-01-01~12-31 을
캐시해두어도 2024-01-02~12-31 요청은 미스다.

일자별로 쪼개니 겹치는 날짜가 재사용되면서 히트율이 올랐다.

그런데 이 변경이 다음 문제를 낳았다. 범위 조회가 날짜 수만큼 왕복하게 되어 2년치가
4.5초가 됐고 그게 게이트웨이 타임아웃으로 이어져 위의 405 사건이 됐다.

한쪽을 고치면서 다른 쪽을 망가뜨렸다. 캐시 단위를 바꾸면서 그 캐시를 범위로 읽는
경로는 안 봤다.

히트율은 77% 를 봤지만 표본이 적어 대푯값으로 보기 어렵다. 숫자보다 바꾼 것과
잃은 것이 이 항목의 내용이다.

## 추적 라이브러리가 클래스패스에 없었다

`날짜` 2026-08-25 · `그 뒤로` 게이트웨이 pom 에 두 의존성 직접 선언, 이유는 주석으로

분산 추적을 붙였는데 게이트웨이 스팬만 하나도 없었다. 게이트웨이만 리액티브 스택이니
WebFlux 컨텍스트 전파 문제로 봤다. 다른 서비스는 정상이고 메트릭도 정상 수집됐다.

리액티브에서는 요청이 여러 스레드를
옮겨다녀 `ThreadLocal` 기반 컨텍스트 전파가 끊기기 쉽다. 게이트웨이는 프록시라 헤더
전달까지 얽힌다. 근거가 있는 가설이었다.

틀렸다. `mvn dependency:tree` 로 보니 추적 라이브러리 자체가 클래스패스에 없었다.

BOM 을 `<scope>import</scope>` 로 가져오면 `dependencyManagement` 만 오고
`dependencies` 블록은 오지 않는다. Maven 스펙이다. 여섯 서비스 중 넷만 BOM 을 일반
의존성으로 한 번 더 선언해 라이브러리를 받고 있었다.

`management.tracing.*` 설정은 읽히지만 스팬을 만들 구현체가 없어 조용히 무시된다.
에러 로그가 남지 않아 설정만 봐서는 알 수 없었다.

WebFlux 컨텍스트 전파는 Spring Boot 3.x + Reactor 3.5 조합에서 이미 자동으로 처리되고
있었다. 옛 버전의 문제를 현재 버전에 그대로 적용한 오진이었다.

라이브러리가 있는지는 확인하지 않고 동작부터 의심했다.

## 서킷은 한 번도 열린 적이 없었다

`날짜` 2026-08-25 · `그 뒤로` 세 서비스 예외 목록 수정. 서킷 OPEN 과 미등록 알림 추가

Resilience4j 를 붙이고 `recordExceptions` 를 적어뒀으니 장애 격리는 된다고 믿었다.

부하 테스트에서 `fx/latest` 가 500 을 46,350 번 냈는데 **서킷브레이커 실패율이 0** 이었다.
서킷은 끝까지 닫혀 있었다.

`recordExceptions` 에 `HttpServerErrorException` 이 적혀 있었다. 이건 RestTemplate 이
던지는 예외다. 호출은 Feign 으로 하므로 `FeignException` 계열이 나온다. 나열된 것만
실패로 세기 때문에 500 을 아무리 받아도 실패가 아니었다.

고치는 데 두 번 틀렸다. `FeignException$ServerError` 라는 클래스는 없다.
5xx 부모는 `FeignServerException`, 4xx 부모는 `FeignClientException` 이다.
없는 이름을 적으면 `ClassNotFoundException` 으로 애플리케이션이 아예 뜨지 않는다.
확인 없이 푸시했다가 서비스를 세웠다.

설정 문자열은 컴파일러가 잡아주지 않는다. 설정 리포는 컴파일 단계가 없어서 코드보다
위험하다.

그리고 설정만 넣어두고 도는지는 안 봤다. market-data 를 내렸다 올려
OPEN → CLOSED 를 눈으로 보고서야 확인이 끝났다.

## rate limit 은 전체 합쳐 200/s 였다

`날짜` 2026-08-26 · `그 뒤로` maxTrustedIndex(1) 로 XFF 신뢰. 앱 한계 측정은 아직

`ipKeyResolver` 를 `@Primary` 로 두었으니 IP 하나당 200/s 로 걸릴 터였다.

```java
String clientIp = exchange.getRequest().getRemoteAddress().getAddress().getHostAddress();
```

`getRemoteAddress()` 는 **직전 홉의 주소**다. 운영은 Traefik 이 앞에 있어서 게이트웨이

Redis 기반이라 게이트웨이 파드를 늘려도 합은 그대로다. 스케일아웃이 처리량을 늘리지
못하는 상태였다.

로컬에서는 k6 나 브라우저가 게이트웨이에 직접 붙어 실제 IP 가 보이므로 정상 동작한다.
운영에서만 나타나는 종류라 로컬 테스트로는 영영 안 보인다.

## 힙이 컨테이너의 25% 를 그냥 잡고 있었다

`날짜` 2025-11-26 · `그 뒤로` -Xmx 명시, GC 후 남는 양 기준 메모리 알림

t3.xlarge(16GB) 에서도 서비스 여섯 개를 띄우면 여유가 없었다. 더 큰 인스턴스가

키우기 전에 실제 사용량부터 쟀다.

user-service   실제 151MB  /  할당 768MB

"메모리가 부족하다" 의 원인은 설정 부재였다. 트래픽도 누수도 아니었다.

## maxSurge 25% 가 단일 노드를 멈췄다

`날짜` 2025-12-02 · `그 뒤로` maxSurge 0 · maxUnavailable 1. 게이트웨이만 maxSurge 1

`helm upgrade` 를 하면 EC2 가 응답하지 않았다. 롤링 업데이트 기본값은 무중단용이니
배포 설정은 의심하지 않았다. 배포 순간에만 생기고 평시에는 멀쩡했다.

쿠버네티스 롤링 업데이트의 기본값은 `maxSurge: 25%` 다. 기존 파드를 유지한 채 새 파드를
먼저 띄운다.

단일 노드에서 서비스 여섯 개가 도는 환경에서는 순간 메모리가 두 배 가까이 필요해진다.
노드에 그만한 여유가 없었다. 무중단을 위한 설정 때문에 오히려 전체가 멈췄다.

`maxSurge: 0` / `maxUnavailable: 1` 로 순차 교체로 바꿨다. 서비스별로 수 초의 다운타임이
생기지만 개인 프로젝트의 트래픽 규모에서는 받아들일 수 있는 교환이었다.

## 라벨 때문에 오히려 막혔다

`날짜` 2026-06-03 · `그 뒤로` 허용 포트에 8000 추가. CI 가 렌더한 정책과 containerPort 를 매번 대조

새로 만든 chat-service 에 다른 서비스와 같은 `tier: business-service` 라벨을 붙였다.
NetworkPolicy 의 관리 대상에 들어가니 잘한 일로 넘어갔다.

웹에서 부르면 503 이었다. 게이트웨이 CircuitBreaker 의 fallback 이었고 chat-service
로그에는 요청이 한 건도 안 찍혔다.

NetworkPolicy 의 허용 포트가 8080~8083 뿐이었다. 기존 서비스가 전부 Spring Boot 라
그 범위만 열려 있었고 FastAPI 인 chat-service 만 8000 을 쓴다.

라벨이 있어 정책 적용 대상에는 들어갔는데 허용 포트에 8000 이 없어 모든 ingress 가
차단됐다.

> 라벨을 붙였기 때문에 오히려 막혔다. 라벨이 없었다면 정책 대상이 아니라 통과했을 것이다.

새 서비스가 기존 포트 대역 밖이면 인프라 화이트리스트를 함께 확인한다.
NetworkPolicy, SecurityGroup, Ingress 규칙 모두 포트가 하드코딩돼 있을 수 있다.

## 3,350 rps 는 측정 PC 의 한계였다

`날짜` 2026-08-25 · `그 뒤로` k6 가 429 를 5xx 와 따로 센다. 2026-09-06 에 같은 VPC 의 EC2 에서 342 rps 로 측정

게이트웨이를 우회해 market-data 를 직접 때리니 3,350 rps 가 나왔다. 게이트웨이 통과량
202 rps 와 비교해 "앱은 3,350 까지 견딘다" 로 정리하려 했다.

그 시점의 CPU 를 같이 봤다.

```
market-data 프로세스   38.7%
호스트 전체            67.8%
```

앱이 아니라 측정 환경이 포화한 것이었다. 부하 생성기를 같은 PC 에서 돌렸으니
3,350 은 이 측정 방식의 한계다.

VU 를 50 에서 250 으로 다섯 배 올려도 처리량은 3,368 → 3,339 로 그대로이고 지연만
29.8ms → 177ms 로 여섯 배가 됐다. 이것도 같은 이야기다.

그래서 이 수치를 쓸 때는 조건을 붙이기로 했다. "게이트웨이가 앱 여력의 6% 만
통과시킨다" 는 말할 수 있지만 "앱이 3,350 rps 를 견딘다" 는 말할 수 없다.

rate limit 값을 바꾸지 않은 이유도 이것이다. 앱의 실제 한계를 모르는 상태에서 문을
넓히면 병목을 게이트웨이에서 앱으로 옮기는 것에 그친다.

2026-09-06 에 같은 VPC 의 별도 EC2 에서 다시 쟀다. 파드 CPU 한도 700m 에서 price 조회가
342 rps 였다. 3,350 과 열 배 차이다. 게이트웨이를 거치면 143 rps 로 떨어지고 429 는 한 건도
안 나왔다.

## 적어둔 버전은 존재하지 않았다

`날짜` 2026-08-27 · `그 뒤로` dependencyManagement 항목으로 고정. tomcat 10.1.55

CVE 를 막으려고 BOM 에 버전을 올려 적었고, 그걸로 패치됐다고 봤다.

```xml
<!-- Security patch: Override Spring Cloud Gateway to fix CVE-2025-41243 (CVSS 10.0) -->
<spring-cloud-gateway.version>4.1.12</spring-cloud-gateway.version>
```

실제로 도는 건 4.1.9 였다. 두 겹으로 틀렸다.

첫째, `import` 스코프로 들여온 BOM 은 프로퍼티만 덮어써도 통하지 않는다. Maven 이
임포트된 BOM 안의 `${...}` 를 그 BOM 자기 프로퍼티로 푼다. `dependencyManagement` 에
항목을 같이 둬야 바뀐다. `spring-boot-starter-parent` 를 상속하면 통하는데 이 프로젝트는
parent 없이 BOM 을 import 한다.

둘째, 4.1.12 는 Central 에 없다. 4.1.x OSS 는 4.1.9 가 마지막이고 4.1.10+ 는
Enterprise 전용이다. 항목을 제대로 넣었어도 받아올 수 없었다.

같은 파일의 tomcat 도 프로퍼티만 있어서 적용되지 않고 있었다. 항목과 짝을 맞춰 넣으니
그제서야 10.1.40 이 10.1.55 가 됐다.

스캐너는 안 고친 것만 잡는다.

## 에러 둘의 원인은 하나였다

## Redis 한도 1GB 는 실사용의 100배였다

`날짜` 2026-10-23 · `그 뒤로` maxmemory 256MB · volatile-lru, 컨테이너 한도 384Mi

운영 Redis 에 메모리 한도가 없었다. 넣으면서 1GB 로 잡았다. 넉넉한 게 안전하다고 봤다.

"1GB 가 맞는 선택일까" 를 묻고 재 보니 운영 최고 사용이 10MB 였다. 키는 채팅 대화 · 하루 한도 · 레이트 리밋 · ShedLock · 캐시 모두
만료 시간이 있다. 가장 큰 일자별 캔들 캐시도 키 하나가 종목 하나의 하루치라 약 0.5KB 고, 전 종목 하루치가 다 들어와도 7.5MB 쯤이다.

한도는 쓰는 양을 정하는 값이 아니라 폭주를 막는 값이다. 1GB 면 폭주 때 노드(16GiB)에서 그만큼 먹은 뒤에야 멈춘다. 256MB 로 하고
컨테이너 한도는 메모리 조각 · AOF 다시 쓰기 몫으로 128Mi 를 얹어 384Mi 로 뒀다.

힙 25% 때와 같은 순서였다. 늘리기 전에 잰다.

## z-index 를 올린 창이 확인 창과 알림을 가렸다

`날짜` 2026-10-24 · `그 뒤로` 떠 있는 요소의 z-index 를 상수 한 곳에 두고 순서를 테스트로 고정

마이페이지 창과 가입 완료 창(`z-50`)이 어두운 바탕을 깔아도 AI 채팅 버튼(9000)이 그 위에 밝게 남았다. 로그인 · 검색 창처럼 9999 로
올리면 끝이라고 봤다.

순서를 테스트로 적다 보니 확인 창(`z-50`)과 알림(`z-[60]`)이 올린 창 밑으로 갔다. 탈퇴 창에서 띄운 탈퇴 확인 창은 눌리지 않고, 창 안에서
띄운 알림은 바탕에 가려 흐리다. 탈퇴 확인은 올리기 전에도 같았다. 둘 다 `z-50` 이라 DOM 에서 뒤인 탈퇴 창이 위였다(코드로 본 것,
운영에서는 확인하지 않았다).

순서 전체를 상수 하나에 뒀다. AI 채팅 버튼 9000 < 달력 9050 < 창 9999 < 확인 창 10000 < 알림 10001. 처음엔 확인 창과 알림을 같은 값으로
뒀는데 브라우저에서 확인 창이 알림을 가렸다. 같은 값이면 또 DOM 순서다. 알림을 한 칸 올리고 `elementFromPoint` 로 창 위 확인 창,
그 위 알림을 확인했다.
